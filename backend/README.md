# DeskBot Backend

FastAPI + PostgreSQL backend for DeskBot (Phase 2). Handles user accounts,
device registration, message delivery (web/app → device), and scheduled
messages. WhatsApp content never passes through this service — see
[Privacy & WhatsApp](../docs/API_DOCUMENTATION.md#privacy--whatsapp).

## Stack

- **FastAPI** 0.115 + **Uvicorn**
- **SQLAlchemy** 2.x ORM
- **PostgreSQL** in production, **SQLite** for local dev/tests (same models,
  no code changes needed — see `app/database.py`)
- **python-jose** for user JWTs, **passlib[bcrypt]** for password hashing
- Plain **SHA-256 + hmac.compare_digest** for device-key verification (see
  `app/security.py` for why this differs from bcrypt for passwords)

## Two credential types

| Who | Credential | Used for |
|---|---|---|
| A person (web/app user) | JWT bearer token from `/auth/login` | register devices, send messages, view history, manage schedules |
| A device (ESP32 firmware) | Device key issued once at `/devices/register` | heartbeat, poll for pending messages, ack messages |

The device key is shown **exactly once**, in the registration response.
Store it in `config.h` (or equivalent) on the device — the backend never
returns it again, only its hash.

## Local development

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env        # defaults to a local sqlite file — good enough to start
uvicorn app.main:app --reload
```

API docs: `http://localhost:8000/docs` (Swagger UI, auto-generated by FastAPI).

## Running against real Postgres locally

```bash
docker run -d --name deskbot-pg -e POSTGRES_USER=deskbot -e POSTGRES_PASSWORD=password \
  -e POSTGRES_DB=deskbot -p 5432:5432 postgres:16
# then in .env:
# DATABASE_URL=postgresql://deskbot:password@localhost:5432/deskbot
```

## Tests

```bash
pip install -r requirements.txt   # includes pytest + httpx
pytest -v
```

Tests run against an isolated SQLite file (`test_deskbot.db`), created and
torn down per test function — they never touch your dev/prod database.

> **Note on this delivery:** the sandbox this backend was written in has no
> network access, so `pip install` and `pytest` could not actually be
> executed here. Every file has been statically checked (`ast.parse`) for
> syntax errors, and the code has been reviewed line-by-line against the
> FastAPI/SQLAlchemy 2.x APIs it targets — but please run `pytest` yourself
> as the first step after pulling this down, before deploying.

## Quick manual smoke test (curl)

```bash
# 1. Register a user
curl -s -X POST localhost:8000/api/v1/auth/register \
  -H "Content-Type: application/json" \
  -d '{"email":"you@example.com","password":"supersecret1"}'

# 2. Log in
TOKEN=$(curl -s -X POST localhost:8000/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"you@example.com","password":"supersecret1"}' | python3 -c "import sys,json;print(json.load(sys.stdin)['access_token'])")

# 3. Register a device
curl -s -X POST localhost:8000/api/v1/devices/register \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"device_uid":"DESKBOT-01"}'
# => copy the returned "device_key" — this is what goes in the ESP32's config

# 4. Send a message (replace DEVICE_ID)
curl -s -X POST localhost:8000/api/v1/messages \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"device_id":"DEVICE_ID","body":"Hello DeskBot","priority":"NORMAL"}'

# 5. Simulate the ESP32 polling (replace DEVICE_ID / DEVICE_KEY)
curl -s localhost:8000/api/v1/devices/DEVICE_ID/messages/pending \
  -H "X-Device-Key: DEVICE_KEY"
```

## Directory structure

```
backend/
├── app/
│   ├── main.py           # FastAPI app, CORS, rate limiting, scheduler loop
│   ├── config.py         # env-driven settings (pydantic-settings)
│   ├── database.py       # SQLAlchemy engine/session (Postgres + SQLite)
│   ├── security.py       # password hashing, JWT, device-key hashing
│   ├── deps.py           # auth dependencies (user JWT, device key)
│   ├── rate_limit.py     # simple in-memory sliding-window limiter
│   ├── models/           # SQLAlchemy ORM models
│   ├── schemas/          # Pydantic request/response models
│   ├── routes/           # API route handlers
│   ├── services/         # business logic (kept out of routes)
│   └── tests/            # pytest suite
├── requirements.txt
├── Dockerfile
├── render.yaml
└── .env.example
```

## What's deliberately NOT in Phase 2

- **OTA firmware updates** — architecture note only, see `docs/DEPLOYMENT.md`.
- **Real-time push to the ESP32** — it polls; see
  `docs/API_DOCUMENTATION.md#real-time-architecture` for the upgrade path.
- **WhatsApp message storage** — by design, never touches this backend.
- **Alembic migrations** — `Base.metadata.create_all()` runs at startup for
  now. Fine for a single-owner hobby deployment; add Alembic before this
  schema needs to evolve under real user data.
